Every notification is a record with a status. The service moves it forward; nothing else does. This page follows one record from creation to its terminal state and names the method behind each transition.

## The five statuses

| Status | Meaning | Reached by |
|---|---|---|
| `PENDING_SEND` | Created and not yet delivered. Scheduled notifications sit here until due | <Sw py="create_notification" ts="createNotification" /> |
| `SENT` | An adapter delivered it. The `sent_at` / `sentAt` timestamp is set | A successful <Sw py="send" ts="send" /> |
| `FAILED` | An adapter raised during delivery | A failed <Sw py="send" ts="send" /> |
| `READ` | An in-app notification the user has opened. `read_at` / `readAt` is set | <Sw py="mark_read" ts="markRead" /> |
| `CANCELLED` | Withdrawn before it was sent | <Sw py="cancel_notification" ts="cancelNotification" /> |

The transitions are strict. Only a `PENDING_SEND` record can become `SENT`, `FAILED` or `CANCELLED`; only a `SENT` record can become `READ`. A `FAILED` or `CANCELLED` record can go back to `PENDING_SEND` by [requeueing](#requeueing) it, which retries the same record. `SENT` and `READ` are terminal: to send a delivered notification again, [resend](#resending) it as a new record.

## Create, then send

<Sw py="create_notification" ts="createNotification" /> always writes the record first and returns it. Whether it also sends depends on <Sw py="send_after" ts="sendAfter" />:

- Unset, or a time in the past: the service calls <Sw py="send" ts="send" /> on the new record before returning.
- A time in the future: the record stays `PENDING_SEND` and the call returns at once.

<Py>

```python
import datetime

notification = service.create_notification(
    user_id=user.id,
    notification_type=NotificationTypes.EMAIL,
    title="Trial ending",
    body_template="billing/trial_ending.html",
    subject_template="billing/trial_ending_subject.txt",
    context_name="trial_ending",
    context_kwargs={"user_id": user.id},
    send_after=datetime.datetime.now(tz=datetime.timezone.utc) + datetime.timedelta(days=7),
)
notification.status  # "PENDING_SEND"
```

`send_after` is compared against `datetime.now(tz=utc)`, so pass an aware datetime.

</Py>

<Ts>

```typescript
const notification = await vintasend.createNotification({
  userId: user.id,
  notificationType: 'EMAIL',
  title: 'Trial ending',
  bodyTemplate: './templates/billing/trial-ending.html',
  subjectTemplate: './templates/billing/trial-ending-subject.txt',
  contextName: 'trialEnding',
  contextParameters: { userId: user.id },
  sendAfter: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
  extraParams: null,
});
notification.status; // 'PENDING_SEND'
```

`sendAfter` is required in the input; pass `null` to send immediately.

</Ts>

## Draining scheduled notifications

Nothing in the library runs on a timer. A scheduled record waits until something calls <Sw py="send_pending_notifications" ts="sendPendingNotifications" />, which asks the backend for every `PENDING_SEND` record whose <Sw py="send_after" ts="sendAfter" /> is unset or in the past and sends each one. Call it from whatever already runs periodic jobs for your application; once a minute is a common choice.

<Py>

`send_pending_notifications()` never raises. Each failure is logged against its notification id, and a summary of sent and failed counts is logged at the end. The sync service sends sequentially; `AsyncIONotificationService` sends with `asyncio.gather`.

`vintasend.tasks.periodic_tasks.periodic_send_pending_notifications` is a ready-made entry point for workers. Without an argument it builds the service from the `NOTIFICATION_SERVICE_FACTORY` setting (resolved once per process and cached); with an explicit service it uses that.

```python
# Celery Beat
from celery import Celery
from vintasend.tasks.periodic_tasks import periodic_send_pending_notifications

celery_app = Celery()
send_pending = celery_app.task(periodic_send_pending_notifications)

celery_app.conf.beat_schedule = {
    "vintasend-send-pending": {"task": send_pending.name, "schedule": 60.0},
}
```

```python
# A management command, a cron entry, or any script
service = build_notification_service()
service.send_pending_notifications()
```

</Py>

<Ts>

`sendPendingNotifications()` sends every due record with `Promise.all`. An adapter failure marks that record `FAILED` and does not stop the others. With `raiseErrorOnFailedSend: true`, a record with no adapter for its type or a failing context generator rejects the whole call.

There is no bundled scheduler. Call the method from a cron job, a worker loop, or a scheduled task runner:

```typescript
import cron from 'node-cron';

cron.schedule('* * * * *', async () => {
  await vintasend.sendPendingNotifications();
});
```

The process that runs this needs the same `contextGeneratorsMap` and adapters as the one that created the notifications, since context is generated here.

</Ts>

## What happens on failure

Inside <Sw py="send" ts="send" />, an adapter that throws moves the record to `FAILED`. The record keeps its template, context name and arguments, so it can be inspected and resent later.

<Py>

Error handling is governed by the `raise_on_failed_send` constructor flag.

- `False` (the default): every failure is logged and the remaining adapters still run. `create_notification` returns normally; the stored record is `FAILED`, so re-read it rather than trusting the returned object's status.
- `True`: the failure is raised to the caller as `NotificationSendError` (adapter failed), `NotificationContextGenerationError` (generator failed; the record is also marked `FAILED`), `NotificationQueueServiceMissingError` (background adapter with no queue service), `NotificationMarkFailedError` or `NotificationMarkSentError` (the backend could not record the outcome).

Marking `FAILED` happens before raising, so the record reflects what happened either way. `delayed_send`, the worker half of background sending, follows the same rules, with one addition: `NotificationNotFoundError` propagates regardless of the flag, because an id that resolves to nothing is a wiring problem rather than a failed send. A worker that receives the same id twice skips a record that is already `SENT`, `READ` or `CANCELLED`.

</Py>

<Ts>

Error handling is governed by the `raiseErrorOnFailedSend` option passed to the factory, `false` by default.

- An adapter error is logged, the record is marked `FAILED`, and `send` moves on to the next adapter. This never throws, whatever the option: `FAILED` on the record is the signal.
- A missing adapter for the notification's type and a failing context generator are logged and leave the record untouched with the option `false`; with `true` they throw. A background adapter with no queue service is logged and skipped either way.

`delayedSend`, the worker half of background sending, marks `FAILED` when the adapter throws, and with the option `true` throws for a missing record or a missing background adapter.

</Ts>

## Cancelling

<Sw py="cancel_notification" ts="cancelNotification" /> withdraws a `PENDING_SEND` record. It takes only the notification id and returns nothing.

<Py>

```python
service.cancel_notification(notification.id)
```

Raises `NotificationCancelError` when the record is not pending: already sent, already cancelled, or missing. The Django and SQLAlchemy backends and the in-repo fake keep the row with status `CANCELLED`, and `get_notification` returns it, so a cancelled notification can be [requeued](#requeueing). A backend that deletes cancelled rows instead can only requeue failed ones. Cancelling never deletes attachment files.

</Py>

<Ts>

```typescript
await vintasend.cancelNotification(notification.id);
```

The service delegates to the backend's `cancelNotification` and logs the outcome. Whether a non-pending record throws, and whether the row is marked `CANCELLED` or removed, is the backend's decision; check the backend package you use.

</Ts>

## Updating before it is sent

A pending record can be edited. Both libraries refuse to change the fields that identify the record or that the service manages itself.

<Py>

```python
service.update_notification(
    notification.id,
    send_after=new_date,
    body_template="billing/trial_ending_v2.html",
)
```

`update_notification(notification_id, pin_template_versions=None, **kwargs)` accepts `title`, `body_template`, `context_name`, `context_kwargs`, `send_after`, `subject_template`, `preheader_template`, `adapter_extra_parameters`, `attachments` and `requested_template_version`. After the write, if the record is `PENDING_SEND` and its `send_after` is now unset or in the past, the service sends it immediately, exactly as `create_notification` would. A `FAILED` or `CANCELLED` record can be updated too, and stays where it is until it is [requeued](#requeueing).

Three fields raise rather than change: `tenant` (`TenantReassignmentError`), `git_commit_sha` (`GitCommitShaReassignmentError`) and `used_template_version` (`UsedTemplateVersionReassignmentError`). The last two are written only by the service at send time. `user_id`, `notification_type` and `status` are not in the accepted keyword set at all.

</Py>

<Ts>

```typescript
await vintasend.updateNotification(notification.id, {
  sendAfter: newDate,
  bodyTemplate: './templates/billing/trial-ending-v2.html',
});
```

`updateNotification(notificationId, fields, options?)` takes a `Partial` of the notification minus `id` and `tenant`. Passing `tenant` or `usedTemplateVersion` throws; `gitCommitSha` is typed as `never`. The service persists the update and returns the record. It does **not** send: moving `sendAfter` into the past makes the record due, and the next `sendPendingNotifications` picks it up.

</Ts>

## Resending

<Sw py="resend_notification" ts="resendNotification" /> is the operation behind a dashboard's "retry" button. It does not touch the source record. It clones the source into a new `PENDING_SEND` record with <Sw py="send_after" ts="sendAfter" /> unset, sends the clone, and returns it. The source keeps its id, status and timestamps, so a `FAILED` record stays `FAILED` and the history stays honest.

Two kinds of record are refused: one-off notifications (they have no user record to clone from; recreate them instead) and notifications still scheduled in the future (cancel or update those instead).

<Py>

```python
clone = service.resend_notification(notification.id)
clone = service.resend_notification(notification.id, use_stored_context_if_available=True)
```

The refusals raise `NotificationResendError`. The clone copies the user, type, title, templates, context name and arguments, adapter parameters, tenant and attachments. With `use_stored_context_if_available=True` and a stored `context_used` on the source, the clone is sent with that context verbatim; otherwise context is generated again. Send failures follow `raise_on_failed_send` as above.

</Py>

<Ts>

```typescript
const clone = await vintasend.resendNotification(notification.id);
const same = await vintasend.resendNotification(notification.id, true);
```

A refusal (not found, one-off, scheduled in the future, or `useStoredContextIfAvailable` with no stored context) is logged and the method returns `undefined`; with `raiseErrorOnFailedSend: true` it throws. The clone copies the user, type, title, templates, context name and parameters, `extraParams` and tenant. Its `contextUsed` is set at creation, from the source's stored context or from a fresh generation, and the send is started without being awaited, so the returned clone is still `PENDING_SEND` at the moment it is returned.

</Ts>

## Requeueing

<Sw py="requeue_notification" ts="requeueNotification" /> puts a `FAILED` or `CANCELLED` record back into `PENDING_SEND`, so it is sent again. Unlike resending, it keeps the record: the id, content, template pin, stored context, adapter used, git commit SHA and attachments all stay as they are. It clears <Sw py="sent_at" ts="sentAt" />.

<Sw py="send_after" ts="sendAfter" /> decides when the retry goes out. Left out, the record keeps its own. `None` / `null` means "now". Once the record is pending again, it is due when that value is unset or in the past, and then it is sent at once, the same as on create. An adapter that uses the queue service puts it back on the queue. A future value leaves it for whatever sends pending notifications. The method returns the record as it stands right after requeueing, from before that send.

`PENDING_SEND` is refused because it is already queued. `SENT` and `READ` are refused because requeueing a delivered notification would deliver it twice under one record; resend it instead.

<Py>

```python
service.requeue_notification(notification.id)                   # keep its send_after
service.requeue_notification(notification.id, send_after=None)  # send it now
service.requeue_notification(notification.id, send_after=tomorrow)
```

A refusal raises `NotificationActionError` before anything is written. Branch on its `reason`: `NOT_FOUND` or `INVALID_STATUS`. It also carries `action` (`"requeue"`), `notification_id` and, for a status refusal, `status`. The message names the notification by id only, so it is safe to log. A stored `context_used` is reused for the send rather than generated again. The write goes to the primary backend and then to every additional backend, like every other write.

`REQUEUEABLE_NOTIFICATION_STATUSES` in `vintasend.constants` lists the allowed statuses. Every backend implements `requeue_notification(notification_id, send_after=UNSET)`, which checks the status and writes in one step, so two callers racing cannot both succeed.

</Py>

<Ts>

```typescript
await vintasend.requeueNotification(notification.id);                      // keep its sendAfter
await vintasend.requeueNotification(notification.id, { sendAfter: null }); // send it now
await vintasend.requeueNotification(notification.id, { sendAfter: tomorrow });
```

A refusal throws `NotificationActionError` before anything is written, with `reason` set to `NOT_FOUND` or `INVALID_STATUS`. Test for it with `isNotificationActionError`, which also recognises the error from another copy of the package. `REQUEUEABLE_NOTIFICATION_STATUSES` lists the allowed statuses, and every backend implements `requeueNotification`.

</Ts>

## Repinning to a template version

<Sw py="repin_notification" ts="repinNotification" /> changes which template version a record renders. Use it after publishing a fixed template, to move notifications that were not delivered onto the fix. An update keeps the pin unless the body template changes, so updating cannot do this.

It works on `PENDING_SEND`, `FAILED` and `CANCELLED` records, whether they were pinned before or not. `SENT` and `READ` are refused, because a delivered record's pin records what it was asked to render. Without a version, the record is pinned to the version that the template renderer for its type reports as current. It changes nothing else: it neither sends nor changes the status, so repin a failed notification, then requeue it. Repinning to the version already pinned writes nothing.

<Py>

```python
service.repin_notification(notification.id)                      # the current version
service.repin_notification(notification.id, template_version=4)  # a version you name
service.requeue_notification(notification.id, send_after=None)
```

A `template_version` that is not a non-negative `int` raises `InvalidTemplateVersionError`, a `ValueError`, before anything is read. A `bool` is refused too. Other refusals raise `NotificationActionError` with `reason` set to `NOT_FOUND`, `INVALID_STATUS`, or `NO_TEMPLATE_VERSION` when no version was given and the renderer reports none. A renderer that raises is logged and counts as reporting none. The write goes through `persist_notification_update` on every backend. `REPINNABLE_NOTIFICATION_STATUSES` lists the allowed statuses.

</Py>

<Ts>

```typescript
await vintasend.repinNotification(notification.id);                         // the current version
await vintasend.repinNotification(notification.id, { templateVersion: 4 }); // a version you name
await vintasend.requeueNotification(notification.id, { sendAfter: null });
```

An invalid `templateVersion` throws a `RangeError`. Other refusals throw `NotificationActionError` with `reason` set to `NOT_FOUND`, `INVALID_STATUS` or `NO_TEMPLATE_VERSION`. `REPINNABLE_NOTIFICATION_STATUSES` lists the allowed statuses.

</Ts>

<Callout kind="note" title="In-app notifications and READ">
`READ` only applies to notifications a user can open. <Sw py="mark_read" ts="markRead" /> moves a `SENT` record to `READ`; the backend refuses any other starting status. Listing, counting and bulk marking are covered in the [in-app notifications guide](/vintasend/docs/in-app-notifications/).
</Callout>
